Python · wgpu · UDP

Draw it, touch it, send it.

This project gives you three things with as little code as possible: a window you draw into with one function, shapes that know when the mouse is on them, and a way to send plain strings — or live video — to another program on your network. This guide walks through all of it, one small step at a time.

01The map

Where everything lives, before touching any of it.

02Install

One command. It needs Python 3.11 or newer and nothing else.

Open a terminal in the project folder and run the script for your system. It creates a private Python environment in .venv, installs the packages, and checks that your graphics card answers.

./toolchain/setup-macos.sh

Linux

Rule for the whole guide

Every command is typed from the project root, and always starts with .venv/bin/python. That is the Python that has the packages.

03Your first window

Twelve lines: a window with one circle.

Create a folder examples/03_mine/ and a file main.py inside it:

import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]     # the project root
sys.path.insert(0, str(ROOT / "graphics"))     # where app3d lives

import app3d

app = app3d.App("my first window", size=(640, 400))

def draw_frame():
    app.aa.draw_screen_circle((320, 200), 80, (1.0, 0.55, 0.1))

app.run(draw_frame)
.venv/bin/python examples/03_mine/main.py

Three ideas are in those lines, and they are the whole model:

  1. App is the window. It opens it, connects it to the graphics card and prepares the renderers.
  2. draw_frame is your program. It says what is on screen right now. You never clear the screen and never "show" it: you only list the things to draw.
  3. app.run(draw_frame) is the loop. It calls your function when something changed, and sleeps the rest of the time. Press Esc or close the window to leave it.

What the App gives you

NameWhat it is
app.aaThe renderer. Every draw_… and in_… method is called on it. "aa" means anti-aliased: smooth edges.
app.plainThe same methods with hard, one-pixel edges for 3D lines. Faster, rougher. Interchangeable with app.aa.
app.cursor()The mouse position as (x, y) in window pixels.
app.mouse_down()True while the left button is held.
app.keys_down(), app.key_pressed(name), app.typed()The keyboard (see The keyboard).
app.pan(), app.zoom()The pan and zoom gestures (see Pan and zoom).
app.size()The window size as (width, height).
app.cameraThe 3D camera (see The camera).
app.request_redraw()"Please call draw_frame once more." Safe from another thread.
app.argsThe command-line options (see The loop).
A habit worth taking

Give the renderer a short name at the top of your program: ui = app.aa. The rest of this guide writes ui.draw_….

04Two coordinate systems

The one idea that explains every method name.

The same window holds two different worlds. Each drawing method belongs to one of them, and its name tells you which.

Screen space

Units are pixels of the window. (0, 0) is the top-left corner, x grows to the right, y grows down.

It is exactly what the mouse reports, so a shape and the cursor speak the same language. Things drawn here ignore the camera and always sit on top.

Methods: draw_screen_rect, draw_screen_circle, draw_screen_gradient_rect, draw_screen_gradient_circle, draw_screen_rect_outline, draw_screen_circle_outline, draw_screen_inverted_rect, draw_screen_triangle, draw_screen_line, draw_screen_dashed_line, draw_screen_image, draw_screen_text.

World space

Units are whatever you decide (metres, say). Three numbers (x, y, z); the floor is the x, y plane and z points up.

What you see depends on the camera: orbit, pan and zoom change the picture, not your numbers.

Methods: draw_line, draw_arrow, draw_circle, draw_points, draw_text, draw_image, draw_grid.

Remember

For buttons, panels, handles and anything the mouse touches: screen space. For the thing you are studying — vectors, particles, a model: world space.

05Shapes on the screen

A rectangle, a circle, a triangle, a line, a dashed line, a picture — plus gradients, borders and a frame.

The rounded rectangle

ui.draw_screen_rect(anchor, size, color, radius)
ArgumentMeaningExample
anchorTop-left corner, in pixels.(60, 90)
sizeWidth and height, in pixels.(260, 150)
colorRed, green, blue and optionally alpha, each from 0 to 1.(0.58, 0.25, 0.90, 1.0)
radiusCorner radius in pixels. Optional; 0 means sharp corners.28
PURPLE = (0.58, 0.25, 0.90, 1.0)

ui.draw_screen_rect((60, 90), (260, 150), PURPLE, 28)    # rounded
ui.draw_screen_rect((60, 260), (260, 40), PURPLE)        # sharp: no radius
ui.draw_screen_rect((60, 320), (260, 40), PURPLE, 999)   # a pill: the radius is capped at half the height

The circle

ui.draw_screen_circle(center, radius, color)

ui.draw_screen_circle((500, 165), 75, PURPLE)

A circle is described from its middle, a rectangle from its corner. That is the only asymmetry to remember.

Just the border

ui.draw_screen_rect_outline(anchor, size, color, radius, thickness)
ui.draw_screen_circle_outline(center, radius, color, thickness)

ui.draw_screen_rect_outline((60, 90), (260, 150), ORANGE, 28, 3)     # a 3-pixel border
ui.draw_screen_circle_outline((500, 165), 75, ORANGE, 8)             # a ring

The arguments of the filled shape, plus thickness, the width of the border in pixels (2 by default). The inside is left alone: what was drawn before shows through.

The border lies inside the shape. Its outer edge is exactly the edge the filled method would draw, so the two fit together with the same arguments:

ui.draw_screen_rect(ANCHOR, SIZE, PURPLE, RADIUS)                    # the fill
ui.draw_screen_rect_outline(ANCHOR, SIZE, WHITE, RADIUS, 2)          # its border, drawn after: on top

The inverted rectangle: a frame

ui.draw_screen_inverted_rect(anchor, size, color, radius)

The opposite of draw_screen_rect, with the same arguments: the rounded box stays transparent, and the colour covers everything outside it, up to the edges of the window.

That is how a frame is made, in three lines, in this order:

ui.draw_screen_image(position, size, picture)                        # 1. the content, even larger than the window
ui.draw_screen_inverted_rect(ANCHOR, SIZE, BACKGROUND, RADIUS)       # 2. hide what is outside the box
ui.draw_screen_rect_outline(ANCHOR, SIZE, ORANGE, RADIUS, 3)         # 3. the border of the box

With an opaque colour the outside disappears. With an alpha below 1 it is only dimmed — a spotlight on the box:

ui.draw_screen_inverted_rect(ANCHOR, SIZE, (0, 0, 0, 0.6), RADIUS)   # darken everything but the box

And the question "is the cursor in the frame?" is the hit test you already know, with the same arguments: ui.in_screen_rect(cursor, ANCHOR, SIZE, RADIUS). Chapter 09, Pan and zoom, uses it to switch gestures on and off.

Gradients: several colours in one shape

ui.draw_screen_gradient_rect(anchor, size, stops, colors, direction, radius)
ui.draw_screen_gradient_circle(center, radius, stops, colors, direction)

The same rounded rectangle and the same circle, with the single colour replaced by a gradient. draw_screen_rect and draw_screen_circle are unchanged: these are two more methods.

A gradient is described by two lists of the same length, read side by side, and a direction:

STOPS  = [0.0,  0.25,   0.5,   0.75,   1.0]       # where: positions from 0.0 to 1.0
COLORS = [BLUE, YELLOW, GREEN, ORANGE, RED]       # what: the colour at each position

ui.draw_screen_gradient_rect((90, 50), (90, 400), STOPS, COLORS, (0, -1), 26)     # bottom to top
ArgumentMeaningExample
anchor, size, radiusExactly those of draw_screen_rect: top-left corner, (width, height), corner radius.(90, 50), (90, 400), 26
center, radiusExactly those of draw_screen_circle.(300, 200), 60
stopsA list of floats from 0.0 to 1.0: positions along the gradient.[0.0, 0.5, 1.0]
colorsA list of (r, g, b) or (r, g, b, a): the colour at each stop. Same length as stops.[BLUE, GREEN, RED]
directionWhich way the gradient runs: an (x, y) tuple or a Vec2, of any length. Optional: left to right by default.(0, -1)
directionThe gradient runs
(1, 0)left to right (the default)
(-1, 0)right to left
(0, -1)bottom to top — screen y grows down, so "up" is minus y
(0, 1)top to bottom
(1, 1)from the top-left corner to the bottom-right corner

A few things the two lists can do:

ui.draw_screen_gradient_rect(a, s, [0, 1], [BLUE, RED])                            # the simplest: two colours
ui.draw_screen_gradient_rect(a, s, [0, 0.9, 1], [GREEN, GREEN, RED])              # flat green, red only at the end
ui.draw_screen_gradient_rect(a, s, [0, 0.5, 0.5, 1], [BLUE, BLUE, RED, RED])      # two stops at the same place: a hard edge
ui.draw_screen_gradient_rect(a, s, [0, 1], [(0, 0, 0, 0.8), (0, 0, 0, 0)], (0, 1))     # alpha too: a shadow that fades out

The colour at one position

Sometimes you need the colour of the gradient somewhere else: a label, a lamp, a marker. Ask for it, with the same two lists:

import screen2d

here = screen2d.gradient_color(STOPS, COLORS, 0.6)     # (r, g, b, a) at 60 %
ui.draw_screen_circle((330, 200), 26, here)
Why a gradient is as fast as one colour

The first time a gradient is drawn, its stops are turned into a tiny strip of 256 coloured dots and sent to the graphics card, which keeps it. From then on, for each pixel of the shape, the card only works out how far along the gradient that pixel is and reads the strip there, blending the two nearest dots. That costs the same for two stops or twenty, and nothing is recomputed while you keep drawing the same gradient.

Example 7: a gauge

.venv/bin/python examples/07_gradient_gauge/main.py

A tall gradient rectangle from blue (bottom) to red (top), and a tiny triangle pointing up, drawn on top of it, that the Up and Down arrow keys move. The program remembers one float, level; everything on screen is computed from it:

level = 0.5                                             # 0.0 = bottom, 1.0 = top

def draw_frame():
    global level
    if app.key_pressed("UP", repeat=True):              # repeat=True: keeps moving while held
        level += 0.02
    if app.key_pressed("DOWN", repeat=True):
        level -= 0.02
    level = min(max(level, 0.0), 1.0)                   # stay on the gauge

    ui.draw_screen_gradient_rect((90, 50), (90, 400), STOPS, COLORS, (0, -1), 26)

    tip_y = 420 - level * 340                           # level 0 -> low on the screen, 1 -> high
    ui.draw_screen_triangle((135, tip_y + 16), 22, 16, (0, -1), WHITE)      # drawn after: on top

    here = screen2d.gradient_color(STOPS, COLORS, level)                    # the colour under the marker
    ui.draw_screen_circle((330, tip_y), 26, here)

Note the minus sign in tip_y: a higher level is a smaller y, because screen y grows downward. The keys are explained in The keyboard.

The triangle

ui.draw_screen_triangle(anchor, base, height, direction, color)

ui.draw_screen_triangle((320, 300), 120, 160, (0, -1), PURPLE)      # pointing up
ArgumentMeaningExample
anchorThe middle of the base, in pixels.(320, 300)
baseWidth of the base, in pixels.120
heightDistance from the base to the tip, in pixels.160
directionWhere the height points: an (x, y) tuple or a Vec2. Only where it points matters, not how long it is. Optional: up by default.(0, -1)
color(r, g, b) or (r, g, b, a).PURPLE
antialias=True (default) for smooth edges, False for the plain, fastest triangle.antialias=False

Because direction is just a vector, a triangle can point at anything. Subtract two positions and you have the direction from one to the other:

from vec2 import Vec2

centre = Vec2(320, 200)
to_mouse = Vec2(*app.cursor()) - centre                 # from the centre to the cursor
ui.draw_screen_triangle(centre, 40, 70, to_mouse, YELLOW)        # an arrowhead that follows the mouse

The same vector makes an arrowhead for a line: put the anchor at the end of the line and give the line's own direction.

antialias=True — smooth

The same idea as the rounded rectangle: for each pixel, the distance to the nearest of the three edges, and a one-pixel fade across it. Slanted edges stay clean at any angle.

antialias=False — plain

The three corners are handed to the graphics card as they are, with one flat colour. Nothing is computed per pixel, and an opaque colour is not even blended. Slanted edges show small steps, one pixel high.

The line

ui.draw_screen_line(start, end, color, thickness)

WHITE, ORANGE = (1, 1, 1), (1.0, 0.55, 0.1)

ui.draw_screen_line((60, 40), (580, 40), WHITE)                # thickness 2 by default
ui.draw_screen_line((60, 70), (580, 120), ORANGE, 6)

Two points and a thickness, the full width of the line in pixels. The line is smooth at any angle and its two ends are round, so lines that meet at a point join cleanly: a polygon is just several of them.

The dashed line

ui.draw_screen_dashed_line(start, end, color, thickness, dash, spacing)

ui.draw_screen_dashed_line((60, 160), (580, 160), ORANGE, 6, dash=20, spacing=10)
ArgumentMeaningDefault
start, endThe two end points (x, y), in pixels.
color(r, g, b) or (r, g, b, a).
thicknessFull width of the line, in pixels.2
dashLength of each dash. Dashed line only.10
spacingEmpty space between two dashes. Dashed line only.6

Dashes have square ends, so both lengths are exact whatever the thickness. Three looks from the same method:

ui.draw_screen_dashed_line(a, b, WHITE, 2)                          # the default: 10 on, 6 off
ui.draw_screen_dashed_line(a, b, WHITE, 2, dash=2, spacing=4)       # dotted
ui.draw_screen_dashed_line(a, b, ORANGE, 6, dash=6, spacing=6)      # a row of squares
A long dashed line is not expensive

The dashes are not separate pieces. The whole line is sent to the graphics card as one item, and for each pixel the card decides whether it falls on a dash or in a gap. A line with a thousand dashes costs the same as a solid one.

The picture

ui.draw_screen_image(anchor, size, source)

ui.draw_screen_image((20, 20), (320, 240), "photo.png")

Described like a rectangle: anchor is the top-left corner, size is (width, height). So its hit test is simply ui.in_screen_rect(cursor, anchor, size). source is a file, a Pillow image, a NumPy array or a Texture.

The picture is stretched to the size you give. To keep its proportions inside a box, let screen2d.fit compute the anchor and size:

import screen2d

anchor, size = screen2d.fit((640, 480), (0, 0), app.size())     # a 4:3 picture, centred in the window
ui.draw_screen_image(anchor, size, "photo.png")

Colour and transparency

A colour is three or four numbers between 0 and 1. The fourth, alpha, is how solid the shape is: 1 hides what is behind it, 0.5 lets half of it through, 0 is invisible. Leave it out and it is 1.

ui.draw_screen_rect((0, 0), app.size(), (0, 0, 0, 0.5))   # dim the whole window

What is on top of what

The order of the lines in draw_frame is the order of the layers: what you draw last is on top. Screen shapes are always above the 3D scene.

Why two kinds of corners

radius > 0 — smooth

For each pixel, the graphics card computes one number: its distance to the edge of the shape. Pixels well inside are fully painted, pixels well outside are not, and the pixels on the edge are painted in proportion. This is a signed distance function (SDF), and it is why the curve stays clean at any size and on a Retina screen.

radius = 0 — fast

A straight, upright rectangle needs none of that: the edges of the rectangle are the edges of the pixels. A separate, minimal program just fills them. With an opaque colour it does not even blend. Use it freely for panels and backgrounds.

06Is the mouse on it?

Two questions that answer True or False.

ui.in_screen_rect(cursor, anchor, size, radius)     # -> True / False
ui.in_screen_circle(cursor, center, radius)         # -> True / False
ui.in_screen_line(cursor, start, end, thickness)    # -> True / False
ui.in_screen_triangle(cursor, anchor, base, height, direction)   # -> True / False

Look at the arguments: after cursor, they are the same, in the same order, as the drawing method. Describe a shape once, then use the description twice.

ANCHOR, SIZE, RADIUS = (60, 90), (260, 150), 28

def draw_frame():
    cursor = app.cursor()
    over = ui.in_screen_rect(cursor, ANCHOR, SIZE, RADIUS)
    ui.draw_screen_rect(ANCHOR, SIZE, YELLOW if over else PURPLE, RADIUS)

The rounded corners are respected: a cursor in the empty corner of the box, outside the curve, is not on the shape. Try it:

preview drawn by this page, same maths as the librarymove the mouse over a shape

A thin line is a small target. Nothing forces the test to use the drawn thickness: draw at 2 pixels and test at 12, and the line becomes easy to grab.

over = ui.in_screen_line(cursor, START, END, 12)                  # generous
ui.draw_screen_line(START, END, YELLOW if over else PURPLE, 2)    # thin
These are plain functions

The tests need no window and no graphics card. They also live in graphics/screen2d.py as screen2d.in_rect and screen2d.in_circle, next to two more that return the distance to the edge in pixels (negative inside): screen2d.rect_distance, screen2d.circle_distance and screen2d.line_distance. screen2d.triangle_points(anchor, base, height, direction) returns the three corners of a triangle, for when you need them yourself. Useful for a forgiving button: rect_distance(…) <= 6 also accepts a cursor 6 pixels outside.

07Hover, click, drag

Three recipes. Everything interactive is a variation of them.

Hover

You have just seen it: ask, then pick the colour. Nothing is stored between two frames.

Click

app.mouse_down() is true for as long as the button is held, which is many frames. A click is the single frame where it becomes true. To see that moment, remember the previous answer:

was_down = False
count = 0

def draw_frame():
    global was_down, count
    cursor, down = app.cursor(), app.mouse_down()

    clicked = down and not was_down          # true for exactly one frame
    was_down = down

    over = ui.in_screen_rect(cursor, ANCHOR, SIZE, RADIUS)
    if clicked and over:
        count += 1

    ui.draw_screen_rect(ANCHOR, SIZE, YELLOW if over else PURPLE, RADIUS)
    ui.draw_screen_text(80, 170, f"clicked {count} times", 16.0, (1, 1, 1))

Drag

A drag has a beginning (the click lands on the shape), a middle (the shape follows the cursor) and an end (the button is released). One boolean, dragging, says which part you are in.

position = [320.0, 200.0]      # a list, so it can be changed
grab = (0.0, 0.0)
dragging = False
was_down = False
RADIUS = 46

def draw_frame():
    global dragging, was_down, grab
    cursor, down = app.cursor(), app.mouse_down()

    if down and not was_down and ui.in_screen_circle(cursor, position, RADIUS):
        dragging = True                                    # the beginning
        grab = (position[0] - cursor[0], position[1] - cursor[1])
    if not down:
        dragging = False                                   # the end
    was_down = down

    if dragging:                                           # the middle
        position[0] = cursor[0] + grab[0]
        position[1] = cursor[1] + grab[1]

    ui.draw_screen_circle(position, RADIUS, YELLOW if dragging else PURPLE)

grab is the small distance between the cursor and the centre at the moment of the click. Adding it back keeps the circle from jumping its centre under the cursor. Try the preview below, then remove grab in your own copy to feel the difference.

click the circle and drag itdragging: False

The complete program for hover is examples/01_hover_shapes/main.py; the drag is in examples/02_udp_drag/main.py.

Several things to drag, and a line between them

.venv/bin/python examples/04_linked_circles/main.py

Two circles, each draggable, joined by a dashed line that brightens under the cursor. It is the drag recipe with two small changes:

circles = [[180.0, 220.0], [460.0, 160.0]]     # two centres
dragged = None                                 # which one is held: 0, 1 or None

def draw_frame():
    …
    hovered = None
    for index in (1, 0):                       # the last one drawn is on top: ask it first
        if ui.in_screen_circle(cursor, circles[index], RADIUS):
            hovered = index
            break

    if down and not was_down and hovered is not None:
        dragged = hovered                      # remember WHICH circle, not just "dragging"
    …
    a, b = circles
    on_line = hovered is None and ui.in_screen_line(cursor, a, b, 14)
    ui.draw_screen_dashed_line(a, b, ORANGE if on_line else GREY, 3, dash=12, spacing=8)
    for index, centre in enumerate(circles):
        ui.draw_screen_circle(centre, RADIUS, YELLOW if index in (dragged, hovered) else PURPLE)
Nothing links the line to the circles

There is no "connection" object to keep up to date. The line is drawn from one centre to the other on every frame, so it is always where the circles are. Keep a few values, describe the whole picture from them each time: that is the entire method, for two circles or two hundred.

A ready-made control: the slider

.venv/bin/python examples/06_slider/main.py

A slider is the drag recipe, packaged: a line, a round handle, and a value between a minimum and a maximum. It is an object, because it has something to remember between two frames — its value, and whether it is being dragged. You create it once, then call one method per frame:

from widgets2d import Slider                    # in graphics/

def draw_frame():

    ui.draw_screen_text(380, 205, f"{level:.0f}", 14.0, WHITE)

Nothing new inside

graphics/widgets2d.py is under 200 lines, built only from what this chapter showed: was_down to see the click, a dragging flag, a grab offset, draw_screen_line and draw_screen_circle. Read it, then write your own controls — a checkbox, a button, a knob — the same way: an object that keeps its state, and one draw(app) that returns its value.

08The keyboard

Three questions you can ask it, and which one to use when.

.venv/bin/python examples/05_keyboard/main.py

Press keys: the window shows the keys held at this moment, the latest presses, and the text you typed. Each of the three panels asks the keyboard a different question.

It is the mouse, again

key_down is to a key what mouse_down is to the button: true during the whole hold. key_pressed is the click: the one frame where it becomes true. In section 07 you computed that moment yourself with was_down; for keys, the App does it for you.

The names of the keys

A key that prints something is named by what is printed on it, in upper case: "A", "7", ";". The name follows your keyboard layout: on a French AZERTY keyboard the key next to Tab is "A". The other keys have a word:

Keys are not characters

Typing a capital A is two keys (Shift, then A) but one character. On some keyboards é is one key, on others two. A text field does not care about keys: it wants the characters, and app.typed() gives exactly those — Shift, layout, accents and auto-repeat already applied by the system.

Use key_pressed / key_down

When the key matters, whatever it prints: arrows to move, Space to pause, Enter to validate, a shortcut.

Use typed()

When the text matters: a name, a number, a search field.

Recipe: a text field

How it works underneath

The system does not let a program read the keyboard continuously: it tells the window, once, "this key went down", "this key came up", "this character was typed". The App listens to those three messages. It keeps the list of keys that are down, and it stores the presses and characters until your next draw_frame, hands them to that frame, then forgets them. That is why keys_pressed() and typed() are about "since the previous frame", and why you should read them in every frame.

Good to know

Reactive loop: a frame is drawn when a key goes down, comes up or repeats. Something that must move smoothly while a key is held needs frames in between: run with --refresh 60.

Escape closes the window; you can still see it in keys_pressed() on its way out.

Several keys at once: most keyboards cannot report every combination of three or more ordinary keys. That limit is in the hardware, not in your program.

Font: the built-in font draws the usual ASCII characters; one it does not know (an accented letter) is drawn as ?. The string in your program is still correct.

09Pan and zoom

Two fingers on a trackpad, or a mouse wheel: two numbers per frame.

.venv/bin/python examples/08_map_viewer/main.py

A large map is shown through a rounded frame. Put the cursor in the frame, then pinch or turn the wheel to zoom, scroll with two fingers or drag to pan. Move the cursor out of the frame: the gestures stop working and the border turns grey.

The two questions

dx, dy = app.pan()        # pixels to move the content by, since the previous frame
factor = app.zoom()       # number to multiply the scale by, since the previous frame

When nothing happened they answer (0.0, 0.0) and 1.0, so you can use them without an if: adding zero and multiplying by one change nothing.

Your program does not need to know which system it runs on: it reads app.pan() and app.zoom(), and app.gestures holds one line of text describing what works here, ready to show to the user.

Why the systems differ

The window library receives one kind of message for all of this: "something scrolled". On macOS the project adds what is missing (the real pinch, and whether a scroll comes from a trackpad), so everything is exact. On Windows, the system itself turns a trackpad pinch into "Ctrl + wheel" before any program sees it, which is why Ctrl + scroll zooms. On Linux no desktop passes the pinch on, and under X11 a trackpad scroll looks exactly like a wheel: use Ctrl + scroll to zoom and Shift + scroll or a drag to pan. The Windows and Linux paths are written from how those systems are documented to behave; only macOS could be tried on the machine this guide was written on.

A view is two values

Whatever you show — a map, a drawing, a graph — panning and zooming it needs only two things remembered:

scale = 1.0               # screen pixels per picture pixel: 2.0 = twice as big
offset = [0.0, 0.0]       # where the picture's top-left corner is on the screen

They are the bridge between the two kinds of position, in both directions:

screen_x = offset[0] + picture_x * scale        # picture -> screen: to draw
picture_x = (screen_x - offset[0]) / scale      # screen -> picture: what is under the cursor?

Recipe: pan

dx, dy = app.pan()
offset[0] += dx
offset[1] += dy

Recipe: zoom around the cursor

Multiplying scale alone would zoom around the picture's corner, and what you were looking at would slide away. The point under the cursor must stay under the cursor. Its distance to the corner grows by the same factor as everything else, so the corner must move back by that much:

def zoom_at(point, factor):
    global scale
    offset[0] = point[0] - (point[0] - offset[0]) * factor
    offset[1] = point[1] - (point[1] - offset[1]) * factor
    scale *= factor

zoom_at(app.cursor(), app.zoom())

Recipe: only inside the frame

Ask where the cursor is, and apply the gestures only if the answer is yes. Read the two values on every frame even when you ignore them: they are "since the previous frame", and unread ones are simply dropped.

def draw_frame():
    cursor = app.cursor()
    inside = ui.in_screen_rect(cursor, ANCHOR, SIZE, RADIUS)     # in the frame?

    pan, zoom = app.pan(), app.zoom()
    if inside:                                                    # the switch
        zoom_at(cursor, zoom)
        offset[0] += pan[0]
        offset[1] += pan[1]

    ui.draw_screen_image(offset, (PICTURE_W * scale, PICTURE_H * scale), texture)
    ui.draw_screen_inverted_rect(ANCHOR, SIZE, BACKGROUND, RADIUS)
    ui.draw_screen_rect_outline(ANCHOR, SIZE, ORANGE if inside else GREY, RADIUS, 3)

A drag is treated differently on purpose: it starts only inside the frame, but once started it continues wherever the cursor goes, as in section 07. Example 8 does both, and also keeps the map from being lost off-screen and limits how far one can zoom.

A large picture

from texture3d import Texture

texture = Texture("map.png")          # once, before the loop
…

Create the texture once and draw it every frame. Zoomed in, the picture is far larger than the window; that costs nothing, the graphics card only works on the pixels that are visible. Zoomed out, the smaller copies the texture keeps (its mipmaps, on by default) stop it from shimmering. One side of a picture can be at most 8192 pixels.

About the map

The map of example 8 is computed by the program when it starts — random terrain coloured by height — so nothing is downloaded and the picture belongs to nobody. Imagery from Google Maps and most online map services may not be copied into your own program. To view a real map, pass a picture you have the right to use: --image world.jpg. NASA's "Blue Marble" images are public domain and come in very high resolution.

Why an idle window costs nothing, and when to change that.

This is why draw_frame must describe the whole picture each time, and why it should not wait or sleep itself: it is called, it lists the shapes, it returns.

14Sending strings

Two programs, one of them says something, the other hears it.

The udp_link library sends Python strings between two programs — on the same computer or on two computers of the same network. One side is the server, the other the client; once connected, both can send and receive.

Step 1 — the shared file, link.toml

Both programs must agree on an address, a port and a secret. They read them from network/link.toml:

[link]
server_ip = "127.0.0.1"    # where the client finds the server
bind_ip   = "0.0.0.0"      # where the server listens (0.0.0.0 = everywhere)
port      = 50555
secret    = "a-long-shared-text-of-16-characters-or-more"

Same computer

Keep server_ip = "127.0.0.1". That address always means "this machine". It is the file as shipped: nothing to do.

Two computers

On the server machine, ask for its address:

cd network
python3 -m udp_link ip

Write the answer in server_ip, then copy the same file to both machines.

The secret proves that a message comes from your own programs; make a new one with python3 -m udp_link keygen (from network/). Messages are signed with it, not hidden: do not send passwords.

Step 2 — the simple way: LinkThread

A window already owns the main thread of your program. LinkThread runs the network beside it and leaves you two things: a method to send, and a function that is called when a string arrives.

import sys
from pathlib import Path
ROOT = Path(__file__).resolve().parents[2]
sys.path.insert(0, str(ROOT / "network"))

from udp_link.bridge import LinkThread

def on_text(text):                       # called for every string received
    print("received:", text)

link = LinkThread("server", ROOT / "network" / "link.toml", on_text=on_text).start()
link.send("temperature=21.4")            # returns at once, from any thread
…
link.close()                             # when the program ends

The other program is the same with "client" instead of "server". Start them in any order: the client keeps trying until the server is there, and a string sent before the connection is ready leaves as soon as it is.

MemberMeaning
LinkThread(role, config, on_text=…)role is "server" or "client"; config is the path of the toml file.
.start()Starts the link in the background and returns the object.
.send(text)Queues one string. Never waits.
.close()Stops the link cleanly.
.connectedTrue once the server listens / the client is connected.
.errorNone, or the reason the link stopped (port already used, for instance).
latest_only=TrueThe default. See below.

State or events?

State — latest_only=True

A position, a slider, a temperature: only the newest value matters. If you send faster than the network delivers, older values are replaced by newer ones. The receiver always ends on the last value and never falls behind.

Events — latest_only=False

"button pressed", "door opened": each one matters, in order. Every string is delivered, one after the other.

What to put in the string

Anything. A convention that reads well and needs no library is key=value pairs separated by ;:

text = f"x={x:.1f};y={y:.1f};drag={int(dragging)}"      # sender

from apps._common import parse_kv                        # receiver
values = parse_kv(text)        # {'x': 212.0, 'y': 148.5, 'drag': 1.0}

One string must stay under about 1100 bytes. For more, send several.

The complete way: async

A program with no window can use the library directly. It is written with async / await, and gives you more: who sent a message, whether a send was received, the list of connected clients.

import asyncio
from udp_link import UDPServer, UDPClient, LinkConfig

async def server_side():
    async with UDPServer(LinkConfig.load()) as server:
        msg = await server.recv()                    # wait for one string
        print(msg.text, "from", msg.peer)
        await server.broadcast("temp=21.4")          # to every client

async def client_side():
    async with UDPClient(LinkConfig.load()) as client:
        await client.send("hello")                   # raises DeliveryError if not received
        async for msg in client.messages():          # every string from the server
            print(msg.text)

asyncio.run(server_side())

Ready-made programs to try the link without writing anything are in network/apps/; from the network folder, in two terminals:

python3 -m apps.time_server --config link.toml
python3 -m apps.time_client --config link.toml

The full reference — reliability, idle mode, every option of the toml file — is network/udp_link/README.md.

16Video between two windows

The third example: a camera on side A, its picture on side B.

.venv/bin/python examples/03_udp_video/main.py

Two windows open. Side A shows a moving test pattern with a counter and a clock; side B shows the same picture a few milliseconds later. No camera is needed: the pattern is generated by side A. To use a real camera, name it:

.venv/bin/python examples/03_udp_video/main.py --source 0

Strings and video are opposites

Strings — udp_link

Every string must arrive. The receiver confirms each one; an unconfirmed string is sent again.

Video — video_link

A late picture is worthless. Nothing is confirmed or sent again: a lost picture is skipped and the next one shown, so the stream never falls behind.

Step 1 — VideoThread

The same idea as LinkThread: the network and the camera run beside your window, and you receive ready-to-draw pictures.

Step 2 — one texture, updated

A texture is a picture stored on the graphics card. Creating one has a cost; changing its pixels is cheap. So video uses a single texture for the whole session: created for the first picture, then updated.

from texture3d import Texture

texture = Texture(picture, mipmaps=False)     # once
texture.update(picture)                       # for every later picture

mipmaps=False skips the smaller copies that a picture needs when it lies far away in a 3D scene. Flat on the screen they are useless, and computing them 15 times per second is wasted work.

Step 3 — the whole viewer

def on_frame(picture):                  # runs in the video thread
    app.request_redraw()                # a picture arrived: wake the window

video = VideoThread("client", CONFIG, on_frame=on_frame).start()
texture = None
shown = 0

def draw_frame():
    global texture, shown
    picture = video.latest
    if picture is None:
        return                                  # nothing received yet

    if video.frames != shown:                   # a new picture since the last frame
        shown = video.frames
        if texture is None:
            texture = Texture(picture, mipmaps=False)
        else:
            texture.update(picture)

    anchor, size = screen2d.fit((texture.width, texture.height), (0, 0), app.size())
    ui.draw_screen_image(anchor, size, texture)

app.run(draw_frame)
video.close()
The same pattern as section 15

on_frame only calls app.request_redraw(); the picture waits in video.latest and all the drawing stays in draw_frame. The window is still reactive: it draws once per picture and sleeps in between. Side A is this same code with "server" — its preview is drawn the same way.

Why the texture is created inside draw_frame

Everything that touches the graphics card must happen in the main thread, the one that runs draw_frame. on_frame runs in the video thread: it may store a value and ask for a redraw, never draw or create a texture.

On two computers

Exactly as for example 2: the same network/link.toml on both machines, with server_ip set to the address of the camera machine. Video uses UDP port 50556 (strings use 50555), so the firewall of machine A must let that one in too.

.venv/bin/python examples/03_udp_video/main.py --side a --source 0     # machine A, with the camera
.venv/bin/python examples/03_udp_video/main.py --side b                # machine B

The installer adds OpenCV (cv2), the standard library for cameras and images. Its pictures are NumPy arrays, which the drawing methods accept — with one detail: OpenCV orders the colours blue-green-red, the rest of the world red-green-blue. Reversing the last axis fixes it (VideoThread already does it for you).

18When it does not work

What you seeWhat to do
ModuleNotFoundError: No module named 'wgpu'You used another Python. Start the command with .venv/bin/python, or run the installer again.
No module named 'app3d' / 'udp_link'The two sys.path.insert lines at the top of your file are missing, or parents[2] does not point at the project root (count the folders between your file and the root).
The window is emptySomething must be drawn inside draw_frame, every time. A shape drawn once outside it is gone at the next frame.
A shape is in the wrong placeScreen y grows downward. And a rectangle is placed by its top-left corner, a circle by its centre, a triangle by the middle of its base.
Pinch does nothing (Linux)Linux desktops do not pass the pinch to the window. Hold Ctrl and scroll with two fingers, or use the wheel.
a gradient needs one colour per stopThe stops and colors lists do not have the same length. Count them: one colour for each position.
A gradient runs the wrong wayPosition 0.0 is where the direction comes from. Bottom to top is (0, -1). Or keep the direction and reverse the colours.
A triangle points the wrong way"Up" is (0, -1), not (0, 1): screen y grows downward.
An animation only moves when the mouse movesThat is the reactive loop doing its job. Add --refresh 60, or call app.request_redraw() when your data changes.
Side B stays on "waiting for side A"Same link.toml on both sides? server_ip is the address of the server machine? The firewall of that machine allows UDP port 50555? The two clocks agree within two minutes (or set max_clock_skew = 0 on both)?
Example 3: side B stays on "waiting for side A"The same checks, with UDP port 50556. With --source 0, look at side A first: if its own preview is empty, the camera did not open (permission, or another program is using it).
Address already in useA server is already running on that port — often a previous run still open. Close it, or change port on both sides.
Linux: no window, or "no adapter"Install the Vulkan driver the installer names, or try --backend gl.
Anything else.venv/bin/python toolchain/check_env.py --window tests each layer and names the one that fails.
