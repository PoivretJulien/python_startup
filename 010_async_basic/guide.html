Python · lambda · asyncio

Do other things while you wait.

Most programs spend their time waiting: for the network, for a file, for a user. Async code is the way to use that waiting time for something else, in one thread, without locks everywhere. This course starts with lambda, because Python libraries ask you for small functions all the time, then builds async one word at a time, up to a working network server.

02Lambda

A small function without a name. You will hand one to almost every library you use.

In Python a function is a value, like a number or a string. You can put it in a variable, in a list, and above all you can give it to another function. Libraries rely on this: "sort by this", "when the button is clicked, call this", "run this in 2 seconds". Each this is a function you pass in.

When that function is one short expression, writing a full def three lines above is heavy. lambda lets you write it right where it is used.

examples/01_lambda.py
"""Lambda: a small function without a name."""


def double(x):
    return x * 2


double_too = lambda x: x * 2            # the same function, on one line

print(double(21), double_too(21))

# 1. As a key: "compare the items by this"
people = [("Ada", 36), ("Linus", 28), ("Grace", 45)]
print(sorted(people, key=lambda person: person[1]))
print(max(people, key=lambda person: len(person[0])))


# 2. As a callback: "call this when it is time"
def repeat(times, action):
    for i in range(times):
        action(i)


repeat(3, lambda i: print("step", i))


# 3. To delay a call: "not now, later"
def greet(name):
    print("hello", name)


later = lambda: greet("Ada")            # nothing is printed on this line
print("before")
later()                                 # greet runs here

# 4. The trap: a lambda reads its variables when it is CALLED
wrong = [lambda: i for i in range(3)]
right = [lambda i=i: i for i in range(3)]
print("wrong:", [f() for f in wrong])
print("right:", [f() for f in right])

The shapes it takes

lambda x: x * 2                              # one
lambda x, y=1: x + y                         # two, the second with a default value

You will also read lambdas inside map and filter, in older code and in many libraries:

list(map(lambda x: x * 2, [1, 2, 3]))        # [2, 4, 6]   apply to each item
list(filter(lambda x: x > 1, [1, 2, 3]))     # [2, 3]      keep the items that pass

[x * 2 for x in [1, 2, 3]]                   # the same two, as most people write them today
[x for x in [1, 2, 3] if x > 1]

Calling now, or passing for later

This is the idea that matters most for the rest of the course. Look at the difference of one word:

loop.call_later(2, greet("Ada"))            # WRONG: greet runs NOW, its result (None) is passed
loop.call_later(2, lambda: greet("Ada"))    # RIGHT: a function is passed, it will run in 2 s
loop.call_later(2, greet, "Ada")            # RIGHT too: many APIs accept the arguments after

Parentheses mean "run it now". A library that wants to call your code later needs the function itself, not its result. Wrapping the call in lambda: is the short way to say "here is how to do it, when you are ready".

The trap everybody meets once

A lambda does not copy the variables it uses. It looks them up when it is called. In a loop, every lambda then sees the last value: that is the wrong: [2, 2, 2] line above.

The fix is lambda i=i: …. A default value is computed when the lambda is created, so each one keeps its own i.

What a lambda cannot do

  • One expression only. No if block, no for, no =, no return, no try. (The one-line form a if test else b is an expression, so it is allowed.)
  • No await. A lambda is never an async function. Section 13 shows what to do instead.
  • No name. In an error message it is called <lambda>, which helps nobody.
Rule

If it fits on one line and you use it once, write a lambda. If you need a second line, a comment, or a name to understand it, write a def. Both give exactly the same kind of object.

What does [f() for f in [lambda: n for n in "ab"]] give?

['b', 'b']. Both lambdas read n when they are called, and by then the loop has ended on "b". With lambda n=n: n you get ['a', 'b'].

button.on_click(save(doc)) saves the document as soon as the window opens, and the button does nothing. Why?

The parentheses run save(doc) at once, and its result (None) is what the button receives. Pass a function instead: button.on_click(lambda: save(doc)).

03Why async?

Because a program that waits is a program that does nothing.

Asking a web server for a page takes, say, one second. During that second your computer computes nothing: it waits for bytes to arrive. Ordinary code blocks there, and the whole program stands still. Three requests cost three seconds.

Async code says instead: "this will take a while, go and do something else, wake me when it is ready." The three waits then happen at the same time.

examples/02_blocking_vs_async.py
"""Three slow jobs: one after the other, then all at once."""
import asyncio
import time


def download(name):                     # the ordinary version
    time.sleep(1)                       # stands for a slow network call
    return name + " done"


async def download_async(name):         # the async version
    await asyncio.sleep(1)              # waits WITHOUT holding the program
    return name + " done"


def blocking():
    return [download(n) for n in ("a", "b", "c")]


async def concurrent():
    return await asyncio.gather(
        download_async("a"), download_async("b"), download_async("c"))


start = time.perf_counter()
print(blocking(), f"{time.perf_counter() - start:.1f} s")

start = time.perf_counter()
print(asyncio.run(concurrent()), f"{time.perf_counter() - start:.1f} s")
it prints
['a done', 'b done', 'c done'] 3.0 s
['a done', 'b done', 'c done'] 1.0 s

Do not worry about the new words yet. Notice only that the two versions look almost the same, and that one is three times faster.

When async helps, and when it does not

Good for waiting

Network requests, databases, sockets, web servers, chat bots, reading many files, timers, user interfaces.

The program is slow because it waits for something outside. This is called I/O-bound work. Async can handle thousands of such waits at once.

Not for computing

Resizing images, crunching numbers, compressing, parsing a huge file.

The program is slow because the processor is busy. This is CPU-bound work. Async gives nothing here: there is no waiting to share. Use processes or threads (section 09).

Remember

Async is one thread doing many things by turns. It is not several things computed at the same instant. Concurrency, not parallelism.

04The three words

async def, await, asyncio.run. That is the whole language.

examples/03_coroutine.py
"""async def, await, asyncio.run: the three words."""
import asyncio


async def add(a, b):
    await asyncio.sleep(0.5)            # pretend this takes time
    return a + b


async def main():
    thing = add(1, 2)                   # calling it does NOT run it
    print(type(thing).__name__)         # it is a coroutine: a paused function
    result = await thing                # await runs it and gives the result
    print(result)

    print(await add(10, 20))            # the usual way: call and await at once


asyncio.run(main())                     # the door from normal code into async code
it prints
coroutine
3
30
  1. async def makes a coroutine function. It is a function that is allowed to pause in the middle and continue later.
  2. Calling it does not run it. add(1, 2) runs no line of the body. It gives back a coroutine: the function, ready to start, like a recipe not yet cooked. This is the first surprise for everybody.
  3. await runs it and waits for the result. While it waits, the rest of the program may run. await is the only place where a coroutine can pause.
  4. asyncio.run(main()) starts everything. It creates the event loop, runs main until it ends, and cleans up. One call, at the bottom of the program.

async def f():Anywhere.Declares a function that can pause.
await xOnly inside an async def."Run x, let others work meanwhile, give me the result."
asyncio.run(f())Only in normal code, once.The door from the normal world into the async world.
The mistake of day one

Forgetting await. The line add(1, 2) alone does nothing at all, and Python warns: RuntimeWarning: coroutine 'add' was never awaited. When you see that message, an await is missing.

In ordinary code, outside any async def, what does print(add(1, 2)) show?

Not 3. It shows <coroutine object add at 0x…>, followed by the "never awaited" warning. The body of add did not run at all. From ordinary code the way in is print(asyncio.run(add(1, 2))).

Async spreads upward

To await something you must be inside an async def. So the function that calls you must await you, and be async too, and so on up to main. This is normal: a program is async from the top, or not at all.

05The event loop

The small engine that decides who runs now. Once you see it, nothing is magic.

The event loop keeps a list of coroutines that are ready to continue, and a list of those that are waiting for something. It repeats four steps for the whole life of the program:

Three consequences follow, and they explain every behaviour you will see:

  1. Between two await, nobody can interrupt you. Your code runs alone until it reaches the next await. This is why async code needs far fewer locks than threads.
  2. The switch is voluntary. A coroutine gives the hand back only at an await. It is called cooperative multitasking: everyone must cooperate.
  3. One coroutine that never awaits stops everybody. A long computation or a time.sleep() holds the loop, and all other tasks freeze. See section 09.

The mental picture


A chess master playing twenty boards. They make one move, walk to the next board, make one move, and so on. One player, twenty games in progress. await is "I moved, your turn": the moment the master walks away.








06Tasks


await waits. A task runs in the background. The difference is the whole point.



Here is the second surprise: two await in a row are not concurrent. await means "run this and wait for it", so the second line starts only when the first is finished. To run two things at once you must first start them both, and wait afterwards. Starting is asyncio.create_task.



examples/04_tasks.py


"""await runs one thing and waits. A task runs in the background."""
import asyncio
import time


async def cook(dish, seconds):
    print("  start", dish)
    await asyncio.sleep(seconds)
    print("  ready", dish)
    return dish


async def one_by_one():
    await cook("rice", 1.0)             # wait for the rice...
    await cook("soup", 1.0)             # ...and only then start the soup


async def together():
    rice = asyncio.create_task(cook("rice", 1.0))    # starts in the background
    soup = asyncio.create_task(cook("soup", 1.0))    # starts in the background
    print("  two tasks created, none has started yet")
    await rice                          # now wait for the results
    await soup


async def main():
    for recipe in (one_by_one, together):
        start = time.perf_counter()
        await recipe()
        print(f"{recipe.__name__}: {time.perf_counter() - start:.1f} s")


asyncio.run(main())


it prints

  start soup
  ready soup
one_by_one: 2.0 s

  start rice

  ready rice

You writeWhat happens

Look at the output of together: the line two tasks created, none has started yet comes before start rice. create_task only puts the coroutine in the ready list. It gets the thread when main reaches its next await, exactly as in the viewer of section 05.



a() and b() each wait one second. How long do these two lines take: await a() then await b()?

Two seconds. Each await finishes before the next line begins. For one second: await asyncio.gather(a(), b()), or create two tasks first and await them after.



Keep the task in a variable


The loop does not hold on to your tasks. A task that nothing refers to can be thrown away by Python before it finishes. Always store what create_task returns: in a variable, a list or a set. Better still, use a TaskGroup (next section), which keeps them for you.








07Many at once


Three ways to start a group of coroutines and collect what they return.



examples/05_groups.py


"""Three ways to run many coroutines and collect the results."""
import asyncio


async def fetch(name, seconds):
    await asyncio.sleep(seconds)
    return f"{name} ({seconds} s)"


async def main():
    # gather: results come back in the order you WROTE them
    results = await asyncio.gather(fetch("slow", 0.3), fetch("fast", 0.1))
    print("gather      ", results)

    # TaskGroup: the block ends when every task is finished
    async with asyncio.TaskGroup() as group:
        slow = group.create_task(fetch("slow", 0.3))
        fast = group.create_task(fetch("fast", 0.1))
    print("TaskGroup   ", [slow.result(), fast.result()])

    # as_completed: results come back in the order they FINISH
    jobs = [fetch("slow", 0.3), fetch("fast", 0.1)]
    for finished in asyncio.as_completed(jobs):
        print("as_completed", await finished)

    # one failure: gather can hand the error back as a value
    async def broken():
        raise ValueError("no network")

    results = await asyncio.gather(fetch("fine", 0.1), broken(),
                                   return_exceptions=True)
    print("with errors ", results)


asyncio.run(main())


it prints


gather       ['slow (0.3 s)', 'fast (0.1 s)']
TaskGroup    ['slow (0.3 s)', 'fast (0.1 s)']
as_completed fast (0.1 s)
as_completed slow (0.3 s)
with errors  ['fine (0.1 s)', ValueError('no network')]




  
ToolResultsIf one failsUse it when

  
asyncio.gather(a, b, c)A list, in the order you wrote them.The error reaches you at once; the others keep running. With return_exceptions=True errors come back as values in the list.You want all the results, simply.

  
async with asyncio.TaskGroup()task.result() on each task, after the block.The others are cancelled, the block waits for them, then raises an ExceptionGroup.The jobs belong together: all succeed, or none. The safest default.

  
asyncio.as_completed(jobs)One by one, fastest first.The error is raised when you await that one.You want to show each result as soon as it exists.





A list of any size


The star unpacks a list into arguments, and a generator expression builds the list:


urls = ["a", "b", "c", "d"]
pages = await asyncio.gather(*(fetch(u, 0.1) for u in urls))

async with asyncio.TaskGroup() as group:                 # the same with a group
    tasks = [group.create_task(fetch(u, 0.1)) for u in urls]
pages = [t.result() for t in tasks]



Catching errors from a TaskGroup


Several tasks can fail together, so the group raises a group of errors. except* (with a star) picks the ones of a given type:


try:
    async with asyncio.TaskGroup() as group:
        group.create_task(fetch("ok", 0.1))
        group.create_task(broken())
except* ValueError as errors:
    for error in errors.exceptions:
        print("failed:", error)



Which one?


Start with TaskGroup. It never leaves a forgotten task running behind your back. Reach for gather when you want the results in one line, or want to tolerate failures with return_exceptions=True.








08Timeouts and cancelling


Anything that waits can wait forever. Always decide how long is too long.



examples/06_timeout_cancel.py


"""Stopping work: a time limit, and a cancel by hand."""
import asyncio


async def slow_job(name):
    try:
        print(name, "started")
        await asyncio.sleep(10)
        print(name, "finished")         # never reached below
    except asyncio.CancelledError:
        print(name, "was cancelled, cleaning up")
        raise                           # always let the cancel continue


async def main():
    # 1. a time limit
    try:
        async with asyncio.timeout(0.5):
            await slow_job("job A")
    except TimeoutError:
        print("job A took too long")

    # 2. cancel by hand
    task = asyncio.create_task(slow_job("job B"))
    await asyncio.sleep(0.2)            # let it start
    task.cancel()                       # ask it to stop
    try:
        await task                      # wait until it really stopped
    except asyncio.CancelledError:
        print("job B is gone:", task.cancelled())


asyncio.run(main())


it prints


job A started
job A was cancelled, cleaning up
job A took too long
job B started
job B was cancelled, cleaning up
job B is gone: True



How a cancel really works


    
  
  1. task.cancel() does not kill anything. It leaves a request: "stop at your next await".
    2. 
  
  2. At that await, the exception asyncio.CancelledError is raised inside the coroutine.
    3. 
  
  3. The coroutine may catch it to clean up (close a file, say goodbye to a server), or simply use try … finally.
    4. 
  
  4. It then lets the exception continue with raise. The task ends, marked as cancelled.
    5. 



A timeout is the same mechanism: asyncio.timeout(0.5) cancels what is inside the block when the time is over, and turns the cancel into a TimeoutError for you to catch outside.




  
You writeMeaning

  
async with asyncio.timeout(5):Everything in the block must finish within 5 seconds, or TimeoutError.

  
await asyncio.wait_for(job(), timeout=5)The same for a single call. The older spelling, still fine.

  
task.cancel()Ask one task to stop.

  
task.cancelled()True if it ended because of a cancel.

A task runs while True: total += 1. You call task.cancel(). When does it stop?

Never. A cancel is delivered at an await, and this loop has none. Worse, it never gives the thread back, so the line calling cancel() cannot even run. A long loop in async code needs an await inside (await asyncio.sleep(0) means "let the others run, then continue"), or belongs in a thread or a process.



Do not swallow the cancel


An except asyncio.CancelledError: that does not end with raise makes the task impossible to stop: timeouts and TaskGroup stop working around it. Clean up, then re-raise. A plain except Exception: is safe, because CancelledError is deliberately not an Exception.








09The blocking trap


The number one async bug: one ordinary slow call, and the whole program freezes.



Remember section 05: a coroutine gives the hand back only at an await. A function that takes one second without any await inside holds the event loop for one second. No other task runs: no heartbeat, no other client served, no timeout checked.



examples/07_blocking_trap.py


"""One blocking call freezes everything. to_thread is the way out."""
import asyncio
import time


async def heartbeat():
    while True:                         # a sign of life every 0.25 s
        print("  tick")
        await asyncio.sleep(0.25)


def heavy():                            # ordinary, blocking code
    time.sleep(1)
    return "heavy result"


async def main():
    beat = asyncio.create_task(heartbeat())
    await asyncio.sleep(0)              # let the heartbeat start

    print("WRONG: calling blocking code directly")
    heavy()                             # the loop is stuck here for 1 s
    await asyncio.sleep(0.1)

    print("RIGHT: sending it to a thread")
    print(" ", await asyncio.to_thread(heavy))

    beat.cancel()


asyncio.run(main())


it prints


  tick
WRONG: calling blocking code directly
  tick
RIGHT: sending it to a thread
  tick
  tick
  tick
  tick
  heavy result





What blocks, and what to write instead



  
BlockingIn async code

  
time.sleep(1)await asyncio.sleep(1)

  
requests.get(url)An async library (httpx, aiohttp), or await asyncio.to_thread(requests.get, url)

  
open(path).read() on a big or slow fileawait asyncio.to_thread(Path(path).read_text)

subprocess.run(…)await asyncio.create_subprocess_exec(…)

  
A long computationawait loop.run_in_executor(pool, work, data) with pool = concurrent.futures.ProcessPoolExecutor() created once: another process, another processor core





asyncio.to_thread(function, arguments…) runs an ordinary function in a separate thread and lets you await its result. It is the bridge to every library that was not written for async.



Thread or process?


A thread is enough when the blocking function waits (a file, a network library, input). When it computes in pure Python, threads take turns on one processor core, so use a process pool to really use a second core.



Which one freezes the other tasks: await asyncio.sleep(5) or time.sleep(0.5)?

time.sleep(0.5), although it is ten times shorter. The first one hands the thread back for five seconds. The second one keeps it for half a second, and nothing else can run.



Find them automatically


Run your program in debug mode: python3 -X dev your_program.py. asyncio then prints a warning each time one step holds the loop for more than 0.1 second, with the name of the guilty line.








10Limits and locks


A thousand tasks at once is easy to write. It is rarely what the other side wants.



examples/08_limits_and_locks.py


"""Semaphore: at most N at a time. Lock: one at a time."""
import asyncio
import time

start = time.perf_counter()


def clock():
    return f"{time.perf_counter() - start:.1f} s"


async def download(n, gate):
    async with gate:                    # wait here if 2 are already inside
        print(clock(), "start", n)
        await asyncio.sleep(0.5)


async def add_money(account, lock):
    async with lock:                    # read, wait, write: nobody in between
        balance = account["balance"]
        await asyncio.sleep(0.01)
        account["balance"] = balance + 10


async def main():
    gate = asyncio.Semaphore(2)
    await asyncio.gather(*(download(n, gate) for n in range(6)))
    print(clock(), "all downloaded")

    account = {"balance": 0}
    lock = asyncio.Lock()
    await asyncio.gather(*(add_money(account, lock) for _ in range(5)))
    print("balance:", account["balance"])


asyncio.run(main())


it prints


0.0 s start 0
0.0 s start 1
0.5 s start 2
0.5 s start 3
1.0 s start 4
1.0 s start 5
1.5 s all downloaded
balance: 50





Do I need a lock at all?


Much less often than with threads. Nobody can interrupt you between two await, so this is perfectly safe without any lock:


account["balance"] = account["balance"] + 10      # no await in the middle: safe


A lock becomes necessary only when an await sits between reading a value and writing it back, as in add_money above. Remove the async with lock: line there and the balance ends at 10 instead of 50: the five tasks all read 0, all wait, all write 10.



Ten tasks run counter["n"] += 1 on the same dictionary. Do they need a lock?

No. There is no await inside that line, so no other task can run in the middle of it. With threads the answer would be yes. This is the main comfort of async code.

11The queue


The cleanest way for tasks to talk to each other: one puts, the other takes.





examples/09_queue.py


"""A queue: one side puts work in, workers take it out."""
import asyncio


async def producer(queue):
    for n in range(1, 7):
        await queue.put(n)
        print("produced", n)
        await asyncio.sleep(0.05)


async def worker(name, queue):
    while True:
        n = await queue.get()           # sleeps here while the queue is empty
        await asyncio.sleep(0.2)        # the work
        print(f"   {name} finished {n}")
        queue.task_done()


async def main():
    queue = asyncio.Queue(maxsize=3)    # put() waits when 3 items are waiting
    workers = [asyncio.create_task(worker(name, queue))
               for name in ("worker A", "worker B")]

    await producer(queue)
    await queue.join()                  # until every item is task_done()
    for w in workers:
        w.cancel()                      # they loop forever: stop them
    print("all work done")


asyncio.run(main())

CallWhat it does

  
await queue.put(item)Adds an item. Waits if the queue is full.

  
await queue.get()Takes the oldest item. Waits if the queue is empty.

  
queue.task_done()"The item I took is finished." One call per get().

  
await queue.join()Waits until every item put in has been marked done.

  
queue.qsize()How many items are waiting now.





Why give it a maximum size


Look at the output: after produced 4 the producer has to wait for a worker. With maxsize, a fast producer is slowed down to the speed of the workers instead of filling the memory. This is called back-pressure, and it is free.

"""async with, async for, and the async generator."""
import asyncio
from contextlib import asynccontextmanager


@asynccontextmanager
async def connection(name):
    print("open ", name)                # could await a real connect here
    await asyncio.sleep(0.1)

        yield name.upper()              # the value after "as"
    finally:
        await asyncio.sleep(0.1)
        print("close", name)            # runs even if the block raises

    while n > 0:
        await asyncio.sleep(0.1)        # each value may need a wait
        yield n
        n -= 1


async def main():
    async with connection("db") as db:
        print("using", db)

    async for n in countdown(3):
        print(n)

    squares = [n * n async for n in countdown(3)]
    print(squares)

NormalAsyncWhy an async version exists

  
with x as y:async with x as y:Opening or closing needs a wait: connect to a database, take a lock, close a socket cleanly.

  
for item in x:async for item in x:Each next item needs a wait: the next line from a socket, the next row, the next message.

  
def + yieldasync def + yieldA generator that may await between two values.

You have already used them: async with asyncio.TaskGroup(), async with asyncio.timeout(…), async with lock. The library tells you which form to use; you rarely have to guess.



async for is not concurrent


async for handles the items one after the other. It only lets other tasks run while it waits for the next item. To treat the items at the same time, create a task for each inside the loop, or use a queue with several workers.








13Lambda meets asyncio


Back to section 02: the places where asyncio asks you for "a function to call later".



examples/11_callbacks.py


"""Where lambda meets asyncio: callbacks, and delayed calls."""
import asyncio
import functools
import time


def resize(name, width, height):        # ordinary, blocking code
    time.sleep(0.2)
    return f"{name} resized to {width}x{height}"


async def compute():
    await asyncio.sleep(0.1)
    return 42


async def main():
    loop = asyncio.get_running_loop()

    # 1. call a plain function later
    loop.call_later(0.3, lambda: print("0.3 s passed"))

    # 2. be told when a task finishes
    task = asyncio.create_task(compute())
    task.add_done_callback(lambda t: print("task result:", t.result()))

    # 3. give arguments to a function that will be called for you
    #    (run_in_executor refuses keyword arguments: wrap the call)
    print(await loop.run_in_executor(None, lambda: resize("a.png", width=64, height=64)))
    print(await loop.run_in_executor(None, functools.partial(resize, "b.png", width=32, height=32)))
    print(await asyncio.to_thread(resize, "c.png", 16, 16))     # the simplest

    # 4. a lambda cannot contain await, but it can RETURN a coroutine
    make = lambda: compute()
    print("made:", await make())

    await asyncio.sleep(0.2)            # leave time for the 0.3 s callback


asyncio.run(main())


it prints


task result: 42
a.png resized to 64x64
0.3 s passed
b.png resized to 32x32
c.png resized to 16x16
made: 42



The order of the lines tells the story: the task finished first (0.1 s), then the first resize (0.2 s), then the timer (0.3 s) fired while the second resize was still in its thread.



Three ways to pass arguments


These APIs call your function with no argument, or with positional arguments only. run_in_executor and call_later, for example, refuse width=64. When your call needs more than they allow, you wrap it:



  
WayCodeNote

  
A lambdalambda: resize("a.png", width=64, height=64)Short and readable. Mind the loop trap of section 02.

  
functools.partialpartial(resize, "a.png", width=64, height=64)Freezes the arguments now: no loop trap. Has a readable name in error messages.

  
Arguments afterasyncio.to_thread(resize, "a.png", 64, 64)When the API accepts them, the simplest. to_thread takes keyword arguments too; call_later, call_soon and run_in_executor take positional ones only.





Lambda and await


A lambda is never async, so lambda: await compute() is a syntax error. Two things are still possible:


make = lambda: compute()                 # returns a coroutine: someone must await it
result = await make()

async def on_click():                    # more than one await? write a real async def
    data = await compute()
    await save(data)


The first form is common for retries and factories: "here is how to build the job, each time you need a fresh one". A coroutine can be awaited only once, so a function that makes a new one is useful:


async def retry(make_job, times):
    for attempt in range(times):
        try:
            return await make_job()      # a new coroutine at every attempt
        except OSError:
            await asyncio.sleep(1)
    raise TimeoutError("gave up")

page = await retry(lambda: fetch("slow", 0.3), times=3)



A callback is not a coroutine


The function given to call_later or add_done_callback is a plain function: it runs inside the loop and must return quickly, without waiting. To start async work from a callback, create a task: lambda: tasks.add(asyncio.create_task(job())) (keeping the task in a set, as section 06 asks).



In modern code


You need callbacks much less than in older tutorials. result = await something() replaces "call this function when the result is there". Keep callbacks for timers, for libraries that demand them, and for the border with non-async code.








14A complete program


Everything together: a TCP server that answers three clients at the same time, in about forty lines.



examples/12_echo_server.py


"""A complete program: a TCP server and three clients, in one event loop."""
import asyncio

HOST, PORT = "127.0.0.1", 8888


async def handle(reader, writer):       # runs once PER client, as a task
    async for line in reader:           # one line at a time, until the client leaves
        text = line.decode().strip()
        print(f"server: got {text!r}")
        writer.write(f"echo: {text}\n".encode())
        await writer.drain()            # wait until the bytes are really sent
    writer.close()
    await writer.wait_closed()


async def client(name, delay):
    reader, writer = await asyncio.open_connection(HOST, PORT)
    for word in ("hello", "bye"):
        writer.write(f"{name} says {word}\n".encode())
        await writer.drain()
        answer = await reader.readline()
        print(f"{name}: received {answer.decode().strip()!r}")
        await asyncio.sleep(delay)
    writer.close()
    await writer.wait_closed()


async def main():
    server = await asyncio.start_server(handle, HOST, PORT)
    async with server:                  # the server listens inside this block
        async with asyncio.TaskGroup() as group:
            group.create_task(client("ann", 0.2))
            group.create_task(client("bob", 0.3))
            group.create_task(client("cat", 0.1))
    print("all clients left, server closed")


asyncio.run(main())


it prints


server: got 'ann says hello'
server: got 'bob says hello'
server: got 'cat says hello'
ann: received 'echo: ann says hello'
bob: received 'echo: bob says hello'
cat: received 'echo: cat says hello'
server: got 'cat says bye'
cat: received 'echo: cat says bye'
server: got 'ann says bye'
ann: received 'echo: ann says bye'
server: got 'bob says bye'
bob: received 'echo: bob says bye'
all clients left, server closed



Read the output: the three conversations are mixed. The server did not finish with ann before listening to bob. Yet there is no thread and no lock anywhere in the file.



What you can recognise



  
LineSeen inWhat it does here

  
asyncio.start_server(handle, …)02A function passed as a value: asyncio calls handle for each client that connects, each in its own task.

  
async for line in reader12The next line needs a wait; other clients are served meanwhile.

  
await writer.drain()11Back-pressure: do not write faster than the network sends.

  
async with server12Closes the listening socket at the end of the block, whatever happens.

  
asyncio.TaskGroup()07Runs the three clients and waits for all of them.

"""Practice 2: ten downloads, three at a time, 0.9 second in all."""
import asyncio
import time

start = time.perf_counter()


async def fetch(n, gate):
    async with gate:                            # three seats
        await asyncio.sleep(0.2 * (n % 3 + 1))  # 0.2, 0.4 or 0.6 s
        return f"page {n}"


async def main():
    gate = asyncio.Semaphore(3)
    tasks = [asyncio.create_task(fetch(n, gate)) for n in range(10)]
    received = 0
    try:
        async with asyncio.timeout(0.9):
            for finished in asyncio.as_completed(tasks):
                page = await finished
                received += 1
                print(f"{time.perf_counter() - start:.1f} s  {page}")
    except TimeoutError:
        for task in tasks:
            task.cancel()                       # do not leave the rest running
        print(f"time is over: {received} of {len(tasks)} pages received")


asyncio.run(main())

3 · A chat server


Copy examples/12_echo_server.py and change the server: a line sent by one client must reach all the other clients, and not the one who wrote it. Test it with two clients that listen and one that speaks.


Hint: the server has to remember who is connected. Think about what happens to that memory when a client leaves, even badly.


solutions/03_chat_server.py

"""Practice 3: a chat server. What one client writes, all the others read."""
import asyncio

HOST, PORT = "127.0.0.1", 8889
clients = set()                         # the writers of everyone connected


async def handle(reader, writer):
    clients.add(writer)
    try:
        async for line in reader:
            for other in clients:       # no await in this loop: nobody can
                if other is not writer: # join or leave while we walk the set
                    other.write(line)
    finally:
        clients.discard(writer)         # also when the client vanishes
        writer.close()
        await writer.wait_closed()


async def listener(name):
    reader, writer = await asyncio.open_connection(HOST, PORT)
    line = await reader.readline()      # sleeps until somebody speaks
    print(f"{name} heard: {line.decode().strip()}")
    writer.close()
    await writer.wait_closed()


async def speaker(name):
    reader, writer = await asyncio.open_connection(HOST, PORT)
    await asyncio.sleep(0.2)            # let the listeners arrive
    writer.write(f"{name}: hello everyone\n".encode())
    await writer.drain()
    writer.close()
    await writer.wait_closed()


async def main():
    server = await asyncio.start_server(handle, HOST, PORT)
    async with server:
        async with asyncio.TaskGroup() as group:
            group.create_task(listener("bob"))
            group.create_task(listener("cat"))
            group.create_task(speaker("ann"))
    print("everybody left")


asyncio.run(main())


bob heard: ann: hello everyone
cat heard: ann: hello everyone
everybody left


The loop over clients contains no await, so the set cannot change while it is being walked: section 10 again, used on purpose.

The messages you will meet, and what each one means.

can't open file '…/examples/01_lambda.py'The terminal is not in the python_async folder. cd python_async, then run the command again.

SyntaxError: 'await' outside async functionThe surrounding function is a plain def (or a lambda). Make it async def.

  
<coroutine object … at 0x…> printed instead of a valueSame cause: you printed the recipe, not the dish. await it.

Everything freezes for a momentA blocking call holds the loop: time.sleep, requests, a long computation. Section 09; find it with python3 -X dev.
